# 客户端主动防御技术方案 · 需求文档（PRD）

> 版本：v0.1（草案）
> 日期：2026-10-14
> 适用端：Android 客户端 / 安全 SDK
> 关联文档：[风控规则分级_按维度.md](风控规则分级_按维度.md)
> 状态：待评审

---

## 1. 背景与目标

### 1.1 背景
现有安全 SDK 可识别高风险机型（改机、Root、Frida/Xposed 注入、模拟器、云机、群控等），但以**被动上报**为主。实测数据显示：
- 存在 **Root 用户在真实操作**的样本，纯 Root 难以彻底防御；
- 部分检测被对抗绕过（`except_error`、服务端标签全 0），强特征组合规则几乎不命中；
- 高危机型一旦被注入/逆向，可直接读取协议、伪造请求、批量作恶。

### 1.2 目标
在**不新增明显误伤**的前提下，把客户端从"识别 → 上报"升级为"识别 → **分级主动防御**"：

| 编号 | 目标 | 衡量 |
|---|---|---|
| G1 | **反 Frida 注入欺骗**：检测到注入时喂假数据，不打草惊蛇，污染逆向、拖慢对抗 | Frida 注入会话被标记 & 关键数据被投毒率 ≥ 95% |
| G2 | **反 Root 抬门槛**：Root 防不住，但显著提高"被控制 + 高价值作恶"的成本 | 高危机型高价值操作强制服务端二次校验覆盖率 100% |
| G3 | **关键接口分级屏蔽**：高置信攻击时静默降级/断网高损接口，避免资损 | 命中高置信策略的会话，高损接口拦截率 ≥ 99% |
| G4 | **加固与自保护**：加固包、反调试、完整性校验、反注入，提高 SDK 自身被破解门槛 | 自身检测模块被 Hook/绕过的难度显著提升（对抗成本评估） |
| G5 | **低误伤**：主动防御（尤其断网/拦截）只在高置信信号触发 | 真人被激进拦截误伤率 < 0.1% |

### 1.3 非目标
- 不追求"彻底阻止 Root/逆向"（不可能，只做抬门槛与止损）；
- 不做服务端风控引擎本身（本文仅定义端侧与端云联动接口）；
- 不替代业务层风控，只做**技术环境侧**的主动防御。

## 2. 设计原则

1. **分级响应（Graded Response）**：检测置信度 → 响应强度分档，低置信只打标、高置信才喂假/断网。承接风控分级文档的"信号 × 作恶链完整度"思路。
2. **不打草惊蛇（Deception over Blocking）**：对可欺骗的攻击（Frida/Hook 取数），优先"喂假数据"而非崩溃/弹窗；让攻击者以为成功，浪费其时间、污染其产出。
3. **纵深防御（Defense in Depth）**：检测、加固、欺骗、降级、端云校验多层叠加，任一层被绕过仍有兜底。
4. **端云协同、服务端为准**：客户端信号可被篡改，最终风险决策与高价值操作放行以服务端为准，客户端只负责"抬门槛 + 止损 + 情报"。
5. **误伤优先可控**：激进动作（断网/拦截/封禁）必须走高置信 + 可灰度 + 可一键回滚；宁可漏防，不可错杀真人。
6. **隐蔽性（Stealth）**：检测与响应逻辑不暴露明文特征、不集中在一处、响应不可被简单 A/B 对比定位。

## 3. 威胁模型与防御触发条件

### 3.1 攻击者画像与能力
| 攻击者 | 能力 | 典型目标 |
|---|---|---|
| Frida 注入逆向者 | 运行时 Hook、dump 内存、改参数、抓协议 | 破解加密、伪造请求、薅羊毛 |
| Root/Xposed/LSPosed 改机党 | 系统级权限、属性伪装、模块化 Hook | 批量养号、改机绕风控 |
| 群控/云机黑产 | 批量设备、自动化输入、机房规模 | 规模化刷量、刷单 |
| 协议逆向脚本 | 脱机构造请求（不走客户端） | 绕过端侧全部检测 |

### 3.2 防御触发：高风险机型判定（复用风控分级）
主动防御按置信度分档触发，判定口径复用 [风控规则分级_按维度.md](风控规则分级_按维度.md)：

| 置信档 | 触发条件（示例） | 允许的响应强度上限 |
|---|---|---|
| **L3 高置信攻击** | Frida/Hook 注入 + 伪装；Root + 指纹交叉不符；恶意无障碍 + 聚类 | 喂假数据、关键接口断网、拦截 |
| **L2 中置信可疑** | 仅 Root 无注入；有框架不伪装；模拟器/云机单信号；多开 | 功能降级、强制服务端二次校验、静默打标 |
| **L1 低置信异常** | 单纯 adb/vpn/proxy/mock；传感器异常**单条**（实测误伤 ~10%，不得单独触发激进动作） | 仅静默上报，不做任何用户侧动作 |

> ⚠️ 实测教训：传感器异常单条精确率仅 61.7%、误伤 10.05%，**严禁用它单独触发喂假/断网**，只能作为加分项参与 L3 组合判定。

## 4. 功能需求

### 4.1 模块 A：反 Frida 注入 + 蜜罐欺骗（G1，最高优先级）

#### A.1 检测点（多信号，任一命中进入"疑似注入"，≥2 命中升 L3）
- 内存映射扫描：`/proc/self/maps` 中非应用路径的可执行 `.so`、gadget 特征；
- 线程名特征：`gum-js-loop` / `gmain` / `pool-frida` 等；
- 端口/文件：`/proc/net/tcp` 的 27042/27043、`/data/local/tmp/re.frida.server`；
- D-Bus 握手探测、命名管道特征；
- 代码完整性：关键函数首字节 inline-hook 检测、text 段 CRC 校验；
- 反调试：`ptrace` 自附加、`TracerPid`、断点/硬件断点检测。

> 实现要点：检测逻辑下沉 Native、分散多处、随机化执行时机，避免单点被一次性 Hook 掉。

#### A.2 响应：分级欺骗（核心创新点）
| 检测结果 | 响应 |
|---|---|
| 疑似（单信号） | 静默打标，上报covert标志，**不改变行为**（避免误判真人崩溃） |
| 确认注入（L3） | 进入**投毒模式**：被 Hook 的关键 API 返回**自洽的假数据**；标记会话"poisoned"；covert 上报服务端 |

**投毒数据设计（必须"可信且无害"）**：
- 假设备指纹：返回一套结构合法、但与真实不符、且被服务端加盐可识别的假 `deviceid/fingerprint`；
- 假业务数据：关键接口返回**语义合理但无价值**的占位数据（空列表、过期/沙箱 token、假余额为 0）；
- 假密钥/签名：加解密/签名入口返回可用但服务端会判伪的结果 → 攻击者构造的请求**必然被服务端拒**，但端侧不报错；
- 原则：**让攻击者"以为成功"**，产出全是污染样本，无法区分真假，拖垮其对抗周期。

**服务端配合**：收到 poisoned 标志的请求 → 影子处理（shadow ban）：正常返回但不入账、不生效、持续喂假、关联打击该设备/账号簇。

#### A.3 不打草惊蛇约束
- 禁止：弹窗、闪退、明显功能缺失、固定错误码 —— 这些会暴露"被检测到了"；
- 投毒必须与正常响应**同路径、同耗时量级**，不可通过时序/异常对比定位。

---

### 4.2 模块 B：反 Xposed / LSPosed（G1）
- 检测：`/proc/self/maps`、`classloader` 异常、LSPosed 管理器包、模块作用域；
- **本 App 是否被纳入 LSPosed 作用域**：读取 LSPosed 作用域库判断；
  > 实现注意：**读取 LSPosed 作用域 DB 必须以 WAL 模式打开**，否则读不到或读到脏数据（见项目记忆 `[[lsposed-scope-db-wal]]`）。
- 响应：同 A.2 分级——确认 Hook 框架且在伪装业务 → 投毒 + 降级；仅存在框架未伪装 → L2 打标 + 二次校验。

---

### 4.3 模块 C：反 Root / 抬门槛（G2）
> Root 不可根除，目标是**抬高"被控制 + 高价值作恶"的成本**，而非阻止 Root 本身。

#### C.1 检测
- su/magisk 路径、`mountinfo`/`attr/prev`(zygisk)、挂载/命名空间不一致；
- Play Integrity：`MEETS_STRONG_INTEGRITY`（硬件背书，最难绕）作为强信号；
- 承接风控分级 §3/§4。

#### C.2 响应（分级抬门槛）
| 情形 | 响应 |
|---|---|
| 仅 Root、无篡改/注入（L2，存在真实用户） | 允许登录，但：① 高价值操作强制服务端二次校验（nonce + 服务端签名）；② 关键业务数据不在端侧明文缓存；③ 降低端侧信任权重 |
| Root + 篡改/注入（L3） | 关键接口降级/断网（模块 D）+ 投毒 + 风险处置 |

#### C.3 抬门槛工程手段（与加固联动）
- **关键逻辑下沉**：核心校验、签名、密钥派生放 Native + 混淆 SO，不在 Java 层暴露；
- **密钥切分**：端侧不持有完整密钥，敏感操作需服务端下发一次性 nonce；
- **设备绑定**：高价值操作绑定硬件背书 attestation，Root 环境无法通过 `STRONG_INTEGRITY`；
- **最小权限**：端侧不存可被 Root 直接读走的高价值数据（Token 短时效、落盘加密）。

---

### 4.4 模块 D：关键接口分级屏蔽 / 断网止损（G3）
> 目标：高置信攻击会话，**静默屏蔽高损接口**，把资损挡在发生前，同时不惊动攻击者。

#### D.1 接口分级（需业务方共同梳理）
| 接口等级 | 示例 | 高置信(L3)时策略 |
|---|---|---|
| 高损（资金/不可逆） | 提现、支付、转账、改绑、批量发送、大额下单 | **静默断网/拒绝**（返回"系统繁忙"类正常话术，不暴露原因） |
| 中损（内容产出） | 发帖、评论、关注、消息 | **降级/限流/延迟生效**（进审核队列、影子发布） |
| 低损（读取展示） | 浏览、详情、配置拉取 | **照常**（维持体验，避免攻击者察觉差异） |

#### D.2 断网/屏蔽实现要点
- 响应形态与正常"网络波动/系统繁忙"一致，**不可有专用错误码**；
- 决策可由端侧先行拦截 + 服务端兜底拒绝（双保险）；
- 全程可灰度、可一键回滚、可按设备/账号簇精准生效。

---

### 4.5 模块 E：加固与自保护（G4，横切）
- **加固包**：SO 加壳/混淆/控制流平坦化，关键字符串加密，反 dump；
- **反调试/反注入自保护**：检测模块自身被 Hook/ptrace 时的自愈与上报；
- **完整性校验**：APK 签名、DEX/SO CRC、资源完整性，防二次打包（关联 `appsign`/`signData`）；
- **通信安全**：协议加密 + 请求签名 + 防重放（时间戳/nonce）+ 证书校验/双向固定，抬高脱机构造请求门槛；
- **多点冗余**：检测/响应逻辑分散、随机化，避免"一处被绕过则全失效"。

## 5. 响应决策矩阵（总表）

| 置信档 | 代表信号 | 静默上报 | 喂假数据 | 功能降级 | 高损接口断网 | 强制服务端二次校验 |
|---|---|---|---|---|---|---|
| **L3 高置信** | Frida注入+伪装 / Root+篡改 / Hook+伪装 / 恶意无障碍+聚类 | ✅ | ✅ | ✅ | ✅ | ✅ |
| **L2 中置信** | 仅Root / 有框架不伪装 / 模拟器·云机单信号 / 多开 | ✅ | ❌（避免误伤） | ✅ | ❌ | ✅ |
| **L1 低置信** | adb/vpn/proxy/mock / 传感器异常单条 | ✅ | ❌ | ❌ | ❌ | ❌ |

> 决策原则：**喂假数据、断网、拦截三类激进动作，仅 L3 允许**；L2 以"抬门槛 + 二次校验"为主；L1 只采集情报。

---

## 6. 端云联动接口（需与服务端对齐）

- 上报：covert 风险标志（poisoned/riskLevel/命中规则/证据摘要），**隐藏在正常请求字段中**，不走显眼独立通道；
- 决策下发：服务端可动态下发"对某设备簇启用 L3 策略 / 调整接口分级 / 关闭某策略"的配置（热更、可灰度）；
- 影子处置：服务端对 poisoned 会话 shadow ban，持续喂假并关联打击；
- 一致性校验：服务端对端侧上报的 `file_* vs java_*`、Integrity 裁决等做二次交叉校验，端侧信号仅作参考。

---

## 7. 可观测性与健康度（承接漏判教训）

- **检测自身健康监控**：`except_error` 批量上升、核心字段 `6666` 屏蔽率上升、"原始信号命中但服务端标签全 0" → 单独告警（当前样本已暴露此问题）；
- 指标：各策略命中量、精确率、**误伤率**（必须盯）、投毒生效率、高损接口拦截量与资损挽回；
- 灰度看板：新策略上线按设备维度灰度，实时对比误伤，异常自动熔断回滚。

---

## 8. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 检测逻辑总 CPU/耗时预算（如冷启动 < Xms、常驻 < X%），不卡主线程 |
| 兼容 | 覆盖主流 ROM/Android 版本，定制 ROM 不误触发 |
| 稳定 | 任何检测/响应异常不得导致 App 崩溃或真人功能不可用（失败安全：异常时退回"仅上报"） |
| 隐蔽 | 响应不可通过时序、错误码、A/B 对比被定位 |
| 可运营 | 全策略可配置、可灰度、可一键回滚、可按簇精准生效 |
| 合规 | 投毒/断网仅针对高置信攻击会话；真人数据与隐私不受影响；保留可申诉/误伤恢复路径 |

## 9. 风险与对抗升级

| 风险 | 应对 |
|---|---|
| 投毒被攻击者识破（时序/对比） | 严格对齐正常响应形态与耗时；随机化；服务端配合 shadow，不在端侧暴露差异 |
| 误伤真人（尤其断网） | 激进动作仅 L3 + 灰度 + 熔断；传感器等高误伤信号禁止单独触发 |
| 检测模块被一次性 Hook 绕过 | Native 下沉 + 多点冗余 + 自保护 + 完整性校验 |
| 脱机协议逆向（不走客户端） | 通信签名/防重放 + 服务端为准 + 行为风控兜底（端侧防御对此天然有限，需服务端补强） |
| 加固/检测引入崩溃或性能问题 | 失败安全设计 + 灰度 + 性能预算卡口 |

## 11. 验收标准（对应目标）

- G1：L3 Frida/Hook 会话投毒生效率 ≥ 95%，无可被定位的暴露特征（红队确认）；
- G2：高危机型高价值操作服务端二次校验覆盖 100%，`STRONG_INTEGRITY` 接入；
- G3：L3 会话高损接口拦截率 ≥ 99%，资损挽回可量化；
- G4：加固 + 自保护使检测模块对抗成本显著上升（红队评估）；
- G5：真人被激进拦截误伤率 < 0.1%，具备一键回滚与误伤恢复。

## 12. 待确认（Open Questions）

1. 高损/中损/低损接口清单需业务方逐一确认；
2. 投毒数据的"可信假值"规格需与服务端共同定义（如何加盐可识别）；
3. covert 上报字段寄生在哪些现有请求字段，需与协议方对齐；
4. `STRONG_INTEGRITY` 对部分合法 Root 开发者/老机型的覆盖与误伤边界；
5. 性能预算具体数值、灰度节奏与熔断阈值。
```
