# 真正的防线:硬件背书 + 服务端

> 这一篇是全套方法论的"地基"。前四篇讲客户端能检测什么、怎么找遗漏、怎么分级;
> 但审查时最该问的一个问题是:**这个 App 是不是只靠客户端自检?** 如果是,无论客户端做得多细,
> 对"掌控本进程的攻击方"本质上都防不住。

---

## 一、为什么客户端进程内自检必败

攻击方(Root + 注入/改机)**完全掌控目标进程的内存与执行**。客户端自检读取的任何进程内数据结构 —— `Build` 字段、`SystemProperties`、`/proc/self/maps`、classloader 的 `dexElements`、`DexFile` 字段 —— 攻击方都能:

- **反射伪造**读到的值(把 `getName()` 改成合法路径);
- **物理移除**痕迹(把注入 dex 元素从数组里删掉,再 hook `findClass` 从内存兜底加载);
- **过滤/喂假**检测函数的输入输出(hook libc `open/read`,让 maps/mountinfo 读到"干净"版本)。

这不是实现没做好,是**结构性上限**:在攻防对抗里,每加一个进程内检测维度,攻击方都能对应加一层伪造;检测方唯一的优势是"不断增加正交维度抬成本",但**不可能根绝**。

> 审查结论里必须写清这一点,避免给出"客户端检测很全就安全了"的错误安全感。

## 二、两类"攻击方够不到"的防线

### 1. 硬件背书证明(Hardware-backed attestation)

- **Play Integrity API** 的 `MEETS_STRONG_INTEGRITY` 裁决,由设备 **TEE / StrongBox** 用硬件密钥签发,Root/改机环境**拿不到** STRONG。机型、系统完整性由硬件根信任背书,伪装层改不了。
- **Key Attestation**(Android Keystore)可证明密钥生成于硬件、设备 bootloader 状态等。
- 局限:部分老机型/定制 ROM 拿不到 STRONG(覆盖与误伤边界需评估);裁决必须在**服务端校验**(客户端拿到的裁决本身也可被篡改,要带 nonce 由服务端验签)。

### 2. 服务端行为风控 + 图谱

- **操作节奏 / 行为序列**:脱离客户端,攻击方的自动化节奏、异常时序在服务端可见。
- **设备-账号关联图谱**:一机多号、同 IP 批量、设备指纹聚类 —— 跨设备跨时间的一致性,客户端伪装再干净也绕不过。
- **多维一致性交叉**:客户端上报的 `file_* vs java_*`、Integrity 裁决、位置 ↔ IP ↔ 时区,由服务端做二次交叉校验,客户端信号仅作参考(可被篡改)。
- **影子处置(shadow ban)**:对高置信攻击会话正常返回但不入账、持续喂假、关联打击,不在端侧暴露"被发现"。

## 三、客户端检测的正确定位

客户端检测**不是没用**,它的价值是:

1. **抬成本 / 拖对抗**:让攻击方每次升级都要投入,降低规模化作恶的性价比。
2. **提供情报**:把端侧信号(即使可被伪造)上报,作为服务端综合评分的**输入之一**,不作最终裁决。
3. **分级响应的触发**:低置信只打标,高置信(且最好有 attestation/服务端佐证)才做激进动作。

一句话:**客户端负责"抬门槛 + 止损 + 情报",最终风险裁决与高价值操作放行以服务端(+硬件背书)为准。**

## 四、审查要点(本篇对应的"遗漏")

对目标 App 逐项核对:

- [ ] 是否接入 **Play Integrity**,并用 `MEETS_STRONG_INTEGRITY` 作为高价值操作的强信号?
- [ ] Integrity 裁决是否**服务端带 nonce 验签**(而非信客户端自报)?
- [ ] 高价值/不可逆操作是否强制**服务端二次校验**(一次性 nonce + 服务端签名)?
- [ ] 是否有**设备-账号图谱 / 行为节奏 / 位置一致性**的服务端兜底?
- [ ] 端侧上报是否只作**参考**,而非最终裁决依据?
- [ ] 关键逻辑/密钥是否**下沉服务端或硬件**,端侧不持有完整密钥?

> 若上述大多为"否",则无论客户端检测清单打了多少勾,整体风控仍是**结构性不足** —— 这是审查里优先级最高的结论。
